# LLM 역할 통합 업그레이드

## 적용 순서와 범위

1. 환자 상태: 현재 증상, 활력징후, 처치 이력, 악화 이벤트를 저장하고 스냅샷 복원 시 보존한다.
2. 악화: 누락된 기준값을 변화량으로 대체하지 않는다. 시각은 도착 후 경과 분으로 해석한다. 증상·활력징후·명시적 중증도 변경을 적용한다.
3. 환자: LLM이 질문에 답할 공개 사실 ID를 선택하고, 코드가 선택된 원문과 고정 문구만으로 답변을 구성한다. 자유 서술 출력이나 알 수 없는 사실 ID는 거부한다. 발병 시점·복용약·현재 증상 질문은 해당 범주의 사실만 제공한다.
4. 병렬 의사 정책: 응급실과 전문과가 관찰된 근거로 질문·검사·협진·처치·진단을 선택한다. 실행은 기존 자원 스케줄러가 담당한다.
5. 기록과 평가: 호출 성공/오류, 모델, 입력 해시, 지연 시간과 근거를 기록한다. 미확정 진단을 성공한 진단으로 계산하지 않는다.

## 실행

기존 데모 및 실험의 기본값은 `demo`로 유지한다. `USE_LLM_FOR_*` 환경 변수만 바꾸어서는 병렬 엔진 모드가 바뀌지 않는다.

실제 세 역할을 사용하려면 다음과 같이 **llm_required를 명시**한다. 처음에는 한 환자로 확인한다.

```powershell
python -m app.scripts.run_live_parallel_visual_multi_patient --fixed-demo --max-cases 1 --clinical-mode llm_required --minute-limit 60
```

웹 서버와 함께 실행:

```powershell
python -m app.scripts.run_live_parallel_web_session --fixed-demo --max-cases 1 --clinical-mode llm_required --minute-limit 60
```

규칙 기반 재현 실행에는 `--clinical-mode demo`를 사용한다.

설정 파일에서는 다음을 기존 flow config에 추가할 수 있다.

```json
{"clinical": {"mode": "llm_required", "max_decisions": 12, "max_questions": 2}}
```

- `OLLAMA_MODEL`: 환자와 응급실 역할. 각 역할의 프롬프트와 관찰 정보는 다르다.
- `SPECIALTY_OLLAMA_MODEL`, `SPECIALTY_BASE_URL`, `SPECIALTY_API_KEY`: 전문과 역할.
- `LLM_TIMEOUT_SECONDS`: 기본 120초. 모델 초기 로딩과 실제 하드웨어에 맞게 조정한다.
- `LLM_MAX_OUTPUT_TOKENS`: 기본 768. 너무 낮으면 JSON이 잘릴 수 있다.
- 자동 API 재시도는 0회다. 의사 결정은 현재 허용 행동을 포함하는 JSON 스키마를 요청하고 별도 검증한다.
- 모델이 없거나, 시간 초과 또는 스키마 오류가 발생하면 실행을 중단한다. 임의의 진료 결정으로 대체하지 않는다.

실행 전 데이터 누락 점검만 수행할 수도 있다. 모델 호출이나 시뮬레이션 없이 `clinical_preflight.json`을 저장한다.

```powershell
python -m app.scripts.run_live_parallel_visual_multi_patient --fixed-demo --preflight-only
```

일반 실행에서도 동일한 점검 보고서를 먼저 저장한다. 기준 활력징후, 검사 목록·결과·점유 시간·자원 매핑, 악화·치료 반응과 출처 정보의 누락을 기록한다. 이는 입력 점검이며 임상적 인증이 아니다.

성공 실행: `outputs/reports/<run_id>/parallel_live_run_summary.json` 및 live viewer 파일.
실패 실행: 같은 디렉터리의 `hospital_failed_run.json`. 실패 당시 상태와 `llm_audit`를 포함한다. 실패 스냅샷은 진단용이며 자동 재개용 체크포인트가 아니다.

## 역할별 정보 경계

| 역할 | 전달하는 정보 | 전달하지 않는 정보 |
|---|---|---|
| 환자 | 환자 병력, 현재 체감 증상 | 정답, 숨겨진 검사 결과, 의사의 진단 메모, 증상 지속 시간과 혼동할 수 있는 시뮬레이션 시계 |
| 응급실 | 초기 공개 정보, 현재 활력징후, 실제 문답, 공개된 검사 결과, 협진 기록 | gold_label, demo 정답 경로, 미공개 검사 결과 |
| 전문과 | 응급실과 같은 관찰 정보 및 요청된 전문과 | gold_label, 미공개 검사 결과 |

`clinical_observation.py`에서 완전한 case 대신 역할별 자료를 만든다. 자유 서술 병력 자체에 정답이나 검사 결과가 들어 있는지는 데이터셋 별도 검수가 필요하다.

검사 목록은 `available_tests` 이름 목록을 사용한다. 없으면 시나리오가 제공하는 `hidden_test_results`의 **이름만** 사용한다. 따라서 연구용으로는 환자마다 정답 검사만 나열하지 말고 공통 검사 목록을 제공해야 한다. 결과가 없는 검사는 `missing`으로 기록하며 소견이나 수치를 만들어내지 않는다.

## 시간 경과와 치료 데이터

엔진 입력은 다음과 같이 설정할 수 있다. 아래 수치와 처치는 소프트웨어 검사 전용 예시이며 임상 모수가 아니다.

```json
{
  "temporal_profile": {
    "arrival_time_min": 0,
    "natural_history_events": [
      {"minute": 10, "changes": {"spo2_delta": -2, "new_symptoms": ["synthetic breathlessness"], "health_state": "Worsening"}}
    ],
    "interventions": {
      "synthetic_support": {"delay_minutes": 2, "effect": {"spo2_delta": 1, "resolved_symptoms": ["synthetic breathlessness"]}}
    },
    "deterioration_model": {
      "triggers": [
        {"if_unaddressed_for_minutes": 20, "addressed_by": "synthetic_support", "effect": {"spo2_delta": -2}}
      ]
    }
  }
}
```

- `natural_history_events`는 명시적 시간표이며 처치만으로 자동 취소되지 않는다. 치료 여부에 따라 달라져야 하는 효과는 `addressed_by`가 있는 trigger로 작성한다.
- 처치가 효과 발생 시각에 도달해야 해당 `addressed_by` trigger를 억제한다. 관련 없는 처치는 억제하지 않는다.
- `addressed_by`가 없는 기존 trigger는 시간 기반 사건이다. 미처치 여부를 검증했다고 해석하면 안 된다.
- 처치 효과·지연 시간은 데이터에 제공해야 한다. 약물 용량이나 효능을 모델이 만들어내지 않는다.
- `vital_values`에 명시적인 새 측정값을 넣을 수도 있다. 변화량에는 유효한 초기 측정값이 필요하다.
- `flow_deterioration`은 별도 경과/대기 임계값 기반 중증도 모형이다. 자체적으로 활력징후를 만들지 않는다. 회복 사건과 함께 사용하면 이후 임계값 검사에서 다시 악화할 수 있으므로 시나리오 설계 시 두 규칙의 의미를 맞춰야 한다.
- 고정 데모의 `time_progression`은 활력징후·증상·중증도 사건으로 변환한다. `worse/urgent`는 Worsening, `critical`은 Critical이다. 동일한 사건을 trigger로 중복 생성하지 않는다.

## 비용과 종료 규칙

- 대기 중 매 분 LLM을 호출하지 않는다. 임상적 의사결정과 실제 문답 시점만 호출한다.
- 전문과 자문이 필요 없는 사례는 응급실에서 종료한다. 모든 사례에 세 역할을 강제로 호출하지 않는다.
- 이미 진행 중인 검사, 완료한 검사, 동일한 질문을 다시 선택하지 못하게 제한한다. 방문한 전문과는 마지막 자문 이후 객관적 소견·활력징후·현재 증상·중증도가 바뀐 경우에만 다시 선택할 수 있다. 시계와 자문 의견만 바뀐 경우는 제외한다.
- 한 환자의 질문 수와 의사 결정 수를 제한한다. 질문 수 한도는 응급실과 전문과가 공유한다.
- 공개된 객관적 소견을 인용하면 supported 진단으로 즉시 종료할 수 있다. 미확정 종료는 의사 결정 한도에 도달했거나 허용된 다음 행동이 없을 때만 가능하다. 남은 행동이 있다는 것이 그 행동의 임상적 유용성을 보장하지는 않는다.
- `certainty=supported`는 적격 객관적 소견을 최소 하나 인용해야 한다. 병력·활력징후·협진 의견만으로는 이 조건을 충족하지 못한다. 이는 보수적인 소프트웨어 조건이며, 병력이나 활력징후만으로 가능한 진단도 미확정으로 남을 수 있다.
- 근거 인용과 의학적 입증은 다르다. 관련 없는 정상 검사 결과를 모델이 잘못 해석하는 경우까지 차단하지 못한다. 감사 기록의 `clinical_support_verified`는 `false`이며 임상적으로 검수된 진단 기준과 독립 평가 데이터가 추가로 필요하다.
- `diagnosis_unresolved` 사례는 진단/진료과 정확도에서 실패로 포함하고 TTD에서는 미확정으로 제외한다.
- `completed`는 진단 에피소드 종료다. `zone=diagnostic_episode_complete`, `disposition_status=not_assessed`로 기록한다. 종료 시 자원 반환은 진단 시뮬레이션 경계이며 실제 퇴원·입원 승인이나 회복을 의미하지 않는다. 화면의 완료 구역 명칭도 `Diagnostic episode complete`로 표시한다. 기존 장면의 `discharge_*` 슬롯 ID는 완료 기록을 배치하는 레이아웃 호환용으로 남아 있다.

## 남아 있는 범위와 필요한 데이터

- `app.main`, `run_single_case`, 기존 단일 환자 뷰어는 여전히 하이브리드 의사 정책이다. 환자의 동적 상태와 질문 보존은 개선했지만 전체 자율 LLM 모드는 위 병렬 실행 명령을 사용한다.
- 과거 단일 엔진의 전체 LLM 호출 수는 새 병렬 `llm_audit`와 동일한 완전성으로 해석할 수 없다.
- 임상적으로 검증된 악화율, 치료 반응, 재평가 간격, 독립적 정답·워크플로 평가 데이터가 필요하다.
- 처치는 설정된 상태 효과만 실행한다. 투약 장비·간호사 점유, 용량, 지속 주입, 약물 상호작용은 아직 모델링하지 않는다.
- LLM 모드에서 명시적 중증도 상승은 재평가 요청을 생성한다. 침상이 배정된 대기 환자를 응급실 우선 대기열로 이동시키고, 검사 결과가 미도착이어도 남은 호출 한도 내에서 문진·처치·협진을 선택할 수 있다. 검사 예약·자원 점유·결과 이벤트는 보존하며 미도착 결과가 있으면 진단 종료를 금지한다. 이미 배정된 의사가 있으면 그 의사의 다음 판단에서 바뀐 상태를 관찰한다. 진행 중인 검사나 다른 환자의 의사 서비스를 강제로 중단하는 선점은 구현하지 않았다.
- 라이브 실행은 `BackgroundStepper`의 단일 작업 스레드가 복사된 상태에서 한 단계를 실행한다. 메인 스레드는 마지막으로 확정된 상태와 `waiting_for_model` 알림을 갱신한다. 성공한 단계만 반영하고, 실패 시 부분 상태를 오류 보고서에 별도로 저장한다.
- 모델 대기 중에도 브라우저 조작·대기 상태 갱신은 가능하지만, 가상 임상 시계와 다른 환자의 단계 진행은 함께 일시 정지한다. 여러 환자의 모델 요청을 동시에 처리하는 기능은 아직 아니다. 벽시계 응답 지연을 가상 임상 시간으로 더하지 않는다.
- 대기 알림은 재생 이력에 추가하지 않아 시간·자원 통계나 대화가 중복되지 않는다. 종료 시 실행 중인 요청은 설정된 시간 제한 내에서 정리한다.
- 전문과마다 별도 가중치/LoRA 모델을 자동 선택하는 기능은 없다. 설정된 공통 전문과 모델에 역할을 부여한다.
- 기존 what-if는 데모용이다. LLM 실행에 대한 counterfactual replay는 명시적으로 차단한다. 새 실행으로 비교해야 하며 모델 확률성에 따른 차이를 고려해야 한다.
- UI는 LLM 모드에서 실제 문답과 판단 근거만 표시한다. 미리 작성된 전문과/환자 대화를 덧붙이지 않는다.

## 검증

`python -m unittest discover -s tests -q`

새 테스트는 외부 추론 없이 실제 스케줄러를 구동한다. 역할별 정보 분리, 검사 결과 공개 시점, 전문과 문진/검사, 오류 중단, 질문·호출 한도, 상태 복원, 시간 기준, 누락 활력징후, 치료 효과, 고정 데모 변환, 화면의 가짜 대화 배제를 확인한다. 이는 모델의 의학적 성능을 검증하는 시험은 아니다.

- 고정 데모 5명 모두 종료, 모델 호출 0회. 보고서: `outputs/reports/20260916_215456/parallel_live_run_summary.json`.

- 재실행에서는 전문과 없이 미확정 종료를 선택하기도 했다. 확률적 출력이므로 모든 사례에 동일한 호출 경로를 보장하지 않는다. 최근 실행 기록은 `tmp/llm_actual_smoke_schema.json`이다.
- 초기 점검의 시간 초과·JSON 형식·허용 행동 위반을 계기로 출력 길이/시간 제한, JSON 스키마, 오류 기록을 보강했다.
- 초기 자유 서술 모드에서 '오늘 시작'에 '아침에 일어났을 때' 같은 세부사항을 덧붙이는 현상을 확인했다. 후속 변경에서는 자유 서술을 제거하고 사실 선택 방식으로 전환했다. 답변 문구의 출처 일치는 코드로 보장하지만, 원자료의 정확성과 선택한 사실의 질문 관련성까지 임상적으로 보증하지는 않는다.

## 후속 검증: 사실 선택·화면 응답성

- 검증용 LLM 호출은 추가하지 않았다. 환자 역할은 기존과 같이 한 번 호출하며, `llm_audit.grounding`에 제공한 사실·선택 ID·최종 답변을 남긴다.
- 임상 검사 결과를 묻는 질문에는 사실을 제공하지 않고 모른다고 답하게 한다. 복용약 정보가 없다고 '복용약 없음'으로 단정하지 않는다.
- 현재 상태에서 사라진 증상을 현재 사실 목록에서 제거한다. 명시적으로 현재 증상을 묻는 경우 과거 병력은 선택지에서 제외한다.
- 프롬프트의 표현 자유도는 줄었다. 자연스러운 일인칭 발화가 중요하면 임상적으로 검수된 환자 원문을 데이터에 제공해야 한다.
- 데모 점검 결과 51개 누락·보완 항목: `outputs/reports/20260916_224115/clinical_preflight.json`.
- 백그라운드 실행 데모 결과: `outputs/reports/20260916_224146/parallel_live_run_summary.json`.
- 실제 로컬 모델+백그라운드 실행 점검: `tmp/grounded_background_smoke.json`.
- 후속 자동 테스트 73개 통과. 생성된 뷰어 JavaScript의 `node --check`도 통과했다. 브라우저의 시각적 화면 검수는 별도로 수행하지 않았다.
- 최신 실제 모델 점검에서 발병 시점 질문에 원문의 `Discomfort started today.`만 전달했고, 백그라운드 대기 알림 18회가 전달됐다(검사 간격 0.25초; 일반 실행 기본 1초).
- 데모의 51개 항목은 검사 목록 대체 사용 5건, 검사 점유 시간 18건, 검사 자원 매핑 18건, 치료 반응 5건, 모수 출처 5건이다. 실제 데이터를 받기 전까지 추정값으로 채우지 않는다.

## 후속 수정: 진단 근거와 미확정 종료 제한

- `diagnostic_evidence.py`에서 근거를 객관적 소견·환자 답변·활력징후·협진 의견으로 구분하고 원본 ID를 보존한다. 구조화된 `answer_status=unknown`과 일반적인 누락 문구는 제외한다. `No fever`나 `No lesion detected` 같은 실제 음성 소견은 보존한다. 모든 자유 서술의 불확실성을 이해하는 판별기는 아니다.
- `hospital_llm_policy.py`에서 현재 허용 행동과 진단 확정도 조합을 출력 스키마와 실행 전 검증에 모두 적용한다. 이를 위해 추가 검증용 LLM 호출이나 자동 재시도는 하지 않는다. 계약 위반 출력은 기존대로 오류로 기록하고 중단한다.
- `hospital_parallel_scheduler.py`는 환자 답변의 알려짐/모름 상태를 문답 이력에 저장한다.
- `llm_audit.decision_validation`에는 제외한 근거, 인용한 근거, 미확정 종료 사유를 저장한다. 한도 종료는 `decision_budget_exhausted`, 선택지 소진은 `available_steps_exhausted`로 구분한다.
- 2026-09-17 자동 테스트 80개 통과. 추가된 7개 테스트는 모름 답변과 누락 결과 제외, 음성 소견 보존, 부적격 인용 거부, 조기 미확정 종료 차단, 적격 소견 인용 시 조기 종료, 종료 사유 구분, 실제 스케줄러의 문진→검사→진단 경로를 확인한다.
- 같은 날 실제 로컬 모델 검증은 첫 응급실 호출에서 `APITimeoutError`로 중단됐다(121.391초, 대기 알림 477회). `ollama ps`에서는 `llama3.2:3b`가 GPU에 적재된 상태임을 확인했다. 최신 `tmp/grounded_background_smoke.json`은 이 실패 기록이다. 앞 절의 성공 실행은 이전 버전 기록이며, 이번 종료 제한 및 복수 분기 JSON 스키마를 실제 모델이 끝까지 준수하는지는 아직 검증하지 못했다.

## 후속 수정: 악화 재평가·재협진·종료 상태

- 중증도 상승마다 `reassessment_requested`를 기록하고 실제 다음 판단 시 `reassessment_performed`에 원인과 선택 행동을 남긴다. 같은 상태로 대기하는 매 분마다 모델을 재호출하지 않는다. 중증도 전환은 입력 시나리오의 상태 사건이나 `flow_deterioration` 임계값에 근거한다. 숫자 활력징후의 임상적 위험 임계값을 임의로 추가하지 않았다.
- `reassessment_pending`과 원인은 스냅샷 복원으로 보존한다. 재평가 도중 검사 결과가 도착해도 진행 중인 진료·협진 경로를 덮어쓰지 않는다.
- `clinical_followup.py`의 관찰 서명을 자문 기록에 저장한다. 새 소견 후 같은 전문과 재협진을 허용하며, 자문 종료 후에는 새 서명으로 갱신해 동일 정보로 반복 호출하지 않는다. 기존 서명 없는 스냅샷은 이전 관찰 시점을 알 수 없어 재협진을 보수적으로 제한한다.
- 추가 역할 호출은 실제 재평가 또는 선택된 재협진 때만 발생하며 기존 `max_decisions` 안에서 처리한다. 한도를 소진한 채 결과가 대기 중이면 이를 사유에 명시하고 결과를 기다린다. 긴급 상황에서도 호출 한도를 무제한 확장하지 않는다.
- 지연 0분 처치 효과는 결정 시점에 즉시 적용한다. 진단 후 설정된 생리 변화는 아래 별도 관찰 보고서로 계산할 수 있다. 입원 병상·퇴원 적합성은 모델링하지 않는다.
- 자동 테스트 84개 통과: 추가 4개는 같은 정보 재협진 차단, 전문과가 주문한 결과를 같은 전문과에서 재검토하는 전체 경로, 검사 대기 중 악화→재평가→즉시 처치→결과 수신 경로, 결과 도착과 재평가 경로 보존을 확인한다. 기존 자원 보존·시간 회계 테스트도 함께 통과했다. 실제 모델 검증은 위 시간 초과 한계가 남아 있으며 이번에는 외부 추론 없이 스케줄러와 검증기를 시험했다.
- 의학적 타당성을 높이려면 독립적으로 검수된 진단별 양성/음성 근거 기준, 활력징후 재평가 기준, 처치 반응·지연 데이터, 입퇴원 기준이 필요하다. 현재 코드의 근거 적격성 검사를 임상 검증으로 표시하지 않는다.

## 진단 후 경과 관찰: 추가 모델 호출 없음

`postdiagnostic_followup.py`는 진단 종료 상태의 복사본에 이미 입력된 지연 처치 효과, 자연 경과 사건, 시간 기반 trigger를 적용한다. 새 처치·입퇴원을 결정하지 않으며 기존 자원 통계나 진단 평가를 변경하지 않는다. 중증도 상승은 `review_needed` 이벤트로 남긴다. 실제 재진 호출이나 병상 점유가 있는 입원 시뮬레이션은 아니다.

새 실행에서는 다음 옵션을 추가한다. 웹 세션 명령에도 같은 옵션을 지원한다.

```powershell
python -m app.scripts.run_live_parallel_visual_multi_patient --fixed-demo --followup-minutes 30
```

기존 실행 보고서를 다시 관찰할 수도 있다.

```powershell
python -m app.scripts.run_postdiagnostic_followup --summary outputs/reports/20260916_224146/parallel_live_run_summary.json --minutes 30
```

- 출력: 해당 보고서 폴더의 `postdiagnostic_followup.json`. `--output`으로 별도 경로 지정 가능.
- 환자별 관찰 구간, 변화 시점의 증상·활력징후·중증도, 적용 사건, 관찰 종료 후에도 효과를 기다리는 처치와 데이터 부족 사유를 기록한다. 환자마다 자신의 진단 종료 시점부터 관찰한다.
- 진단 미완료 환자는 사유와 함께 제외한다. 원본 상태의 생리 시계가 진단 종료 시점과 맞지 않거나 실제 시행한 처치의 효과 정의가 없으면 거부한다.
- 추가 병원 대기 시간은 쌓지 않으므로 `queue_wait` 악화는 적용하지 않는다. 명시적 `since_arrival` 규칙은 계속 적용한다. 치료 회복 후 이 규칙이 다시 악화를 만들 수 있으므로 시나리오의 규칙을 검수해야 한다.
- 변화가 없다는 것을 회복으로 해석하지 않는다. `disposition_status=not_assessed`, `clinical_validity_verified=false`를 유지한다. 관찰 데이터는 현재 라이브 화면에 통합하지 않고 JSON 보고서로 제공한다.
- 검증: 기존 저장 실행 5명에 대해 30분 관찰 보고서 생성 성공, 추가 LLM 호출 0회(`tmp/postdiagnostic_followup_check.json`). 지연 효과·이후 악화·원본 보존·저장 보고서 재현·미완료 제외·대기 시간 경계·입력 오류 등을 포함해 자동 테스트 90개 통과.
